Purpose and traceability

This specification tells engineering exactly what to build so that Binance funding requests run only through a dedicated execution service that verifies ops Passkey approvals itself. Every requirement in "Refactor the Binance sending process" maps to a design element and a test below. Infrastructure (projects, network, IAM) is in Platform Design v2; this document covers the service.

Scope: the execution service (internal API, approval UI, WebAuthn verifier, policy engine, executor, reconciliation worker, audit writer, admin UI), its database, its Binance client, the TMS changes, and removal of the old path. Out of scope: TMS business logic, Binance account setup beyond API keys and whitelists.

Terms: instruction = immutable payment order with a version; approval request = instruction hash plus nonce, expiry, operator; approval = verified WebAuthn assertion over one approval request; execution = the single Binance attempt for a payment UUID.

Binance Settlement —

What changes in TMS

  1. Replace every direct Binance call with POST /v1/instructions to the execution service.
  2. Store the returned instruction_id, version and instruction_hash against the payment.
  3. Read results with GET /v1/instructions/{id} (poll every 10 s while not terminal, then stop). Map states: CONFIRMED → paid; FAILED, EXPIRED, CANCELLED, BLOCKED_BY_POLICY → not paid (a new version may be submitted); SUPERSEDED → follow the newer version; PENDING_APPROVAL, APPROVED, RESERVED, SENDING, ACCEPTED → in progress; UNKNOWN, MANUAL_REVIEW → pending, show "being verified".
  4. If business data changes before execution, submit again with the same tms_payment_uuid and version + 1; the service supersedes older versions that are not yet reserved.
  5. Delete the old Binance client code, configuration and secrets; remove the Binance SDK dependency from the main backend build.

What the execution service is not

  • Not a general Binance gateway: only the operations in the policy file, only the endpoints in the Binance integration section.
  • Not a ledger: TMS remains the business system of record; the service is the record for approvals and executions.
  • Not reachable from the internet except the approval origin, and that only through IAP and Cloud Armor.

Process separation inside the execution project

The service runs as three processes, each with its own service account and database role, so that a bug in the internet-facing code cannot reach the Binance key, and the code holding the key accepts no inbound connections.

End-to-end flow

Ops approve a hash of the exact stored instruction; the service verifies it, reserves the payment, sends one request to Binance, and reconciles by order ID whenever the outcome is uncertain.

After ACCEPTED, the reconciliation worker polls withdrawal history until Binance reports a final status, and TMS reads the result through GET /v1/instructions/{id}. With dual approval, steps from "GET /i/{id}" to "POST assertion" happen once per approver.

Payment instruction

An instruction is a flat JSON object whose canonical bytes are hashed once at creation and never change; every approval and the executor work from those stored bytes.

Schema (binance-exec/instruction/v1)

Field Type Validation Notes
schema string equals binance-exec/instruction/v1 Set by the service
tms_payment_uuid string lowercase RFC 4122 UUID Duplicate-protection key
version integer ≥ 1; equals previous max + 1 for this UUID New version supersedes older unreserved ones
operation string in policy operations WITHDRAW initially
source_account string in policy source_accounts Logical name chosen by TMS
binance_account_id string resolved by the service from policy at create time Set by the service; the actual Binance account that pays. Approval covers it
wallet_type integer 0 (spot) or 1 (funding), resolved from policy at create time Set by the service; sent to Binance as walletType. Approval covers it
asset string ^[A-Z0-9]{2,15}$, in policy for that account
amount string canonical decimal (rules below); > 0; scale ≤ asset precision in policy Never a JSON number
beneficiary_address string 1–128 printable ASCII, no whitespace; matches the network's address regex in policy Leading/trailing space is rejected, not trimmed
network string in policy for that asset Binance network code
memo string "" or 1–128 printable ASCII; required when the network's policy says memo_required: true Always present
environment string equals the service's configured environment Set by the service
service_id string equals binance-exec Set by the service

Unknown fields are rejected (additionalProperties: false). TMS supplies tms_payment_uuid, version, operation, source_account, asset, amount, beneficiary_address, network, memo, and optionally tms_creator_id (stored next to the instruction, not in the canonical bytes, and advisory only because TMS controls it). The service sets the rest. There is no timestamp inside the canonical bytes, so an identical retry produces identical bytes; created_at is a database column.

At reserve time the executor resolves source_account against the current policy again; if binance_account_id or wallet_type would differ, the instruction goes to BLOCKED_BY_POLICY and needs a new version.

Canonical decimal

  • Regex: ^(0|[1-9][0-9]*)(\.[0-9]*[1-9])?$.
  • No sign, exponent, leading zeros, trailing fractional zeros, or bare trailing dot.
  • "1250.5" valid; "1250.50", "01250.5", "1.25e3", "1250." rejected with invalid_amount. Rejection (not normalization) means TMS and the service can never disagree on the value.
  • Arithmetic (limits, sums) uses a decimal type, never floating point.

Canonical serialization and hash

  • JSON Canonicalization Scheme, RFC 8785: keys sorted by UTF-16 code units, no whitespace, strings with minimal escaping, integers as plain digits. With the restricted character sets above, this equals sorted-key compact JSON.
  • instruction_hash = SHA-256(utf8(canonical_json)), stored as 32 bytes, shown as lowercase hex.
  • Store canonical_json bytes as received from the canonicalizer. Never re-serialize from parsed fields for hashing or execution.

Internal API

TMS can create, read and cancel instructions over mTLS on the PSC endpoint, and nothing else; there is no way to send approval state.

Transport: HTTPS on 10.10.2.50:8443 (PSC). TLS 1.3 only. Client certificate required, issued by the private CA in prj-exec, subject CN=tms-prod; the service checks the certificate's SPIFFE-style URI SAN spiffe://<domain>/tms against an allowlist. Requests without a valid certificate are dropped at the TLS layer. Bodies are JSON, max 16 KiB, Content-Type: application/json required.

POST /v1/instructions

Request:

{
  "tms_payment_uuid": "7d1f2c9e-4b3a-4c1e-9f55-2a6b8e0d1c42",
  "version": 1,
  "operation": "WITHDRAW",
  "source_account": "binance-main",
  "asset": "USDT",
  "amount": "1250.5",
  "beneficiary_address": "TQ5uGkqQxVq4wJm8mR2s7cH9yK3pLx1aBz",
  "network": "TRX",
  "memo": ""

Behaviour:

  1. Validate against the schema (unknown fields → 400 unknown_field; this is how approved: true is rejected).
  2. Resolve binance_account_id and wallet_type from policy, build the canonical bytes, evaluate create-time policy; on denial → 422 policy_denied with the rule ID.
  3. In one transaction holding the per-payment lock (SELECT … FROM payments WHERE tms_payment_uuid = $1 FOR UPDATE, creating the row if missing): - If (tms_payment_uuid, version) exists with identical canonical bytes → 200 with the existing record (idempotent retry). Different bytes → 409 version_conflict. - If any version of this UUID has an active execution attempt (RESERVED, SENDING, ACCEPTED, UNKNOWN, MANUAL_REVIEW) or is CONFIRMED → 409 already_executing. - Otherwise mark every lower version in PENDING_APPROVAL or APPROVED as SUPERSEDED (their approvals no longer count), insert the new version, audit instruction.created and instruction.superseded, return 201.
  4. The same per-payment lock is taken by cancel and by the executor's reserve step, so a stale version can never be reserved while a newer one is being created.

WebAuthn

The service is the WebAuthn relying party for approve.<domain>: it issues every challenge, verifies every assertion with a maintained library plus its own binding checks, and trusts nothing the browser or TMS says about approval.

Library: use one maintained server library and pin it: py_webauthn (Python), @simplewebauthn/server (Node.js), webauthn4j (Java) or go-webauthn (Go). Do not hand-roll CBOR/COSE parsing. The checks below are what the library does plus what the service must add.

Operator identity before WebAuthn: IAP authenticates the Google account and passes a signed x-goog-iap-jwt-assertion header. The service verifies that JWT (audience = the backend service, issuer https://cloud.google.com/iap) and maps the email to an active operator. The challenge is created for that operator only.

Verification algorithm (POST /i/{id}/assert)

Step 2 commits on its own, so a failed or tampered attempt still burns the challenge; steps 3–9 run in a second transaction. Any failure → approval.rejected audit event naming the failed step, HTTP 400 with a generic message.

  1. Load the challenge row by the challenge bytes from clientDataJSON; it must belong to this instruction, this IAP-authenticated operator and the route's intent (approve or reject, which is a field of the signed approval request).
  2. Consume it: UPDATE challenges SET used_at = now() WHERE id = $1 AND used_at IS NULL AND expires_at > now() must affect exactly one row (expiry and replay). Commit.
  3. Recompute the approval request from stored fields and check SHA-256(canonical) == challenge (binding).
  4. Library verification with expected challenge, expectedOrigin = "https://approve.<domain>", expectedRPID = "approve.<domain>", requireUserVerification = true: - clientDataJSON.type == "webauthn.get"; no crossOrigin: true; topOrigin absent. - rpIdHash == SHA-256("approve.<domain>"); flags UP = 1 and UV = 1. - Signature over authenticatorData || SHA-256(clientDataJSON) verifies with the stored public key for credential_id.
  5. Sign counter: if stored or received counter is non-zero, received must be greater than stored, otherwise reject and raise security.clone_suspected. Update stored counter.
  6. Credential is active (revoked_at IS NULL and active_from <= now()) and belongs to the operator; if policy requires device-bound keys, the backup-eligible flag must be 0.
  7. Operator is active (revoked_at IS NULL, active_from <= now()) and their role's max_amount for the asset covers amount (see Policy for the dual-approval rule).
  8. Lock the instruction: SELECT … FROM instructions WHERE id = $1 FOR UPDATE. It must still be PENDING_APPROVAL, with the same version and instruction_hash as the approval request, and be the highest version for its payment UUID.
  9. Insert the approval or rejection (primary key on instruction + operator, so the same operator cannot count twice), audit it, then — still holding the row lock — count valid approvals (step "Quorum" in Policy) and move to APPROVED if met, or count rejections and move to CANCELLED if rejections_to_cancel is reached. Commit.

Because step 8 locks the instruction row, two approvers finishing at the same moment are serialized and the second one sees the first approval, so quorum is never missed.

Browser side

The approval page calls navigator.credentials.get({ publicKey }) with the options above, base64url-encodes the response fields, and posts them. It never computes or alters the challenge. Use the same library's browser helper (@simplewebauthn/browser or equivalent), self-hosted.

Approval screen

The Passkey prompt shows no transaction details, so this page is what ops actually approve: it must show every execution-relevant field from the stored canonical instruction, and nothing outside the execution service may be able to change it.

Content (top to bottom)

  1. Environment banner: PRODUCTION in red, or STAGING in amber; taken from service config.
  2. Operation and source account (logical name plus the Binance account label from policy).
  3. Amount in large type with the asset, exactly the canonical string, plus a thousands-separated rendering (1,250.5 USDT) labelled "same value".
  4. Destination: network name and code, full address in monospace split into groups of 4 characters, memo (or "none"), and the allowlist entry name from policy ("Treasury cold wallet"). An address not in the allowlist never reaches this page.
  5. TMS payment UUID, version, created time, instruction hash (first 8 + last 8 hex characters, full on click).
  6. Approval status: required count, who has already approved (operator display names), time left on the instruction.
  7. Policy summary: per-transaction limit, today's usage for this account and asset after this payment.
  8. Buttons: Approve with Passkey and Reject with Passkey (a signed rejection with a reason; it does not block other approvers; rejections_to_cancel signed rejections cancel the instruction).

All values are rendered server-side from instructions.canonical_json and policy; the page never takes values from query strings, TMS or local storage.

Accessibility and safety

  • Approve is never the default button and is disabled for 3 seconds after the page loads, so a stray Enter or double click does nothing.

  • The page works without client-side templating; the only script is the WebAuthn call.

Reserve quorum re-computed from the approvals table (never from the state column); everything from Create again with the current policy; binance_account_id and wallet_type unchanged; instruction not expired and is the highest version for its payment; daily sum for this account + asset of executions reserved in the last 24 h in RESERVED, SENDING, ACCEPTED, UNKNOWN, MANUAL_REVIEW, CONFIRMED, plus this amount, ≤ daily_max_per_account RESERVED, or BLOCKED_BY_POLICY

What the roles mean in practice: with the example policy, a 5,000 USDT payment needs one approver or senior approver; a 25,000 USDT payment needs two senior approvers, because each approver must individually cover the amount. If you want a junior approver to co-approve large payments, raise their max_amount; there is no mixed rule.

Daily-limit race: the reserve transaction takes pg_advisory_xact_lock(hashtext(source_account || ':' || asset)) before computing the daily sum, so two executors reserving different payments on the same account and asset cannot both pass the limit.

A policy change never weakens checks on instructions already approved: reserve re-evaluates with the new policy, so a lowered limit blocks pending payments; a raised threshold does not reduce required approvals for instructions created under the old one.

Policy loading

  • File path baked into the image; the service refuses to start if the file is missing, fails schema validation, or environment differs from the runtime config.
  • policy_version and the file's SHA-256 go into the service.started audit event and every decision event.
  • No runtime API changes policy. A change is a pull request to policy/ with you as required reviewer, then a normal deploy.

Execution state machine

Every instruction version moves through one state machine stored in Postgres; a payment has at most one live execution attempt at a time and never another after a confirmed one, and nothing leaves SENDING or UNKNOWN without evidence from Binance or an audited two-admin decision.

Attempts and retries

  • Executions are keyed by (tms_payment_uuid, attempt). Each attempt has its own withdrawOrderId = payment UUID without dashes + a + attempt number (e.g. 7d1f2c9e4b3a4c1e9f552a6b8e0d1c42a1, 34 characters).
  • A partial unique index allows at most one non-final attempt per payment (RESERVED, SENDING, ACCEPTED, UNKNOWN, MANUAL_REVIEW), and no new attempt once any attempt is CONFIRMED.
  • A new attempt is possible only for a new instruction version with fresh approvals, and only when every previous attempt is FAILED or RELEASED.
  • After a two-admin FAILED decision, reconciliation keeps querying that attempt's withdrawOrderId until 7 days after the attempt started. If Binance ever shows it, the attempt becomes CONFIRMED, a critical alert fires (security.late_found), and any later attempt for the same payment is flagged for treasury review as a possible double payment.

Reserve and send (executor loop)

-- tx 1: reserve
BEGIN;
SELECT 1 FROM payments WHERE tms_payment_uuid = $uuid FOR UPDATE;                  -- per-payment lock
SELECT pg_advisory_xact_lock(hashtext($source_account || ':' || $asset));         -- daily-limit lock
SELECT * FROM instructions
 WHERE id = $id AND state = 'APPROVED' AND expires_at > now()
   AND version = (SELECT max(version) FROM instructions WHERE tms_payment_uuid = $uuid)
 FOR UPDATE;                                                                       -- 0 rows => skip
-- quorum from source of truth, never from the state column:
SELECT count(DISTINCT a.operator_id)
  FROM approvals a
  JOIN challenges c  ON c.id = a.challenge_id AND c.used_at IS NOT NULL
  JOIN operators o   ON o.id = a.operator_id AND o.revoked_at IS NULL AND o.active_from <= now()
  JOIN credentials k ON k.credential_id = a.credential_id AND k.revoked_at IS NULL AND k.active_from <= now()
 WHERE a.instruction_id = $id AND a.voided_at IS NULL AND a.intent = 'approve'
   AND a.instruction_hash = $instruction_hash;                                      -- must be >= required
-- application: re-run reserve-time policy incl. daily sum (by executions.reserved_at) and account mapping
INSERT INTO executions (tms_payment_uuid, attempt, instruction_id, state, withdraw_order_id,
                        reserved_at, lease_owner, lease_until)
     VALUES ($uuid, $next_attempt, $id, 'RESERVED', $order_id, now(), $worker_id, now() + interval '60 seconds');
UPDATE instructions SET state = 'RESERVED' WHERE id = $id;
-- audit outbox rows for policy.decision and execution.reserved
COMMIT;

-- tx 2: mark sending, durably, before any network call (lease must still be ours)
UPDATE executions SET state = 'SENDING', attempt_started_at = now(), lease_until = now() + interval '60 seconds'
 WHERE tms_payment_uuid = $uuid AND attempt = $n AND state = 'RESERVED' AND lease_owner = $worker_id;  -- 1 row
UPDATE instructions SET state = 'SENDING' WHERE id = $id;
COMMIT;

-- single Binance call (no automatic retry)

-- tx 3: record outcome
UPDATE executions SET state = 'ACCEPTED' | 'FAILED' | 'UNKNOWN', binance_withdraw_id = ..., last_error = ...,
                      lease_owner = NULL, lease_until = NULL
 WHERE tms_payment_uuid = $uuid AND attempt = $n AND state = 'SENDING' AND lease_owner = $worker_id;
UPDATE instructions SET state = <same> WHERE id = $id;
COMMIT;

Rules:

  • The executor reads only instructions.canonical_json, recomputes its SHA-256 against instruction_hash, and builds the Binance request from those bytes. It never reads TMS data or any mutable column.
  • The HTTP client never retries POST requests; library-level retries are switched off. The total call timeout (10 s) is well under the 60 s lease, and the worker renews its lease every 20 s while a call is open.
  • Lease recovery (any worker, every 30 s): rows whose lease_until < now() are reclaimed — RESERVED → attempt RELEASED, instruction back to APPROVED; SENDING → UNKNOWN. A worker never touches rows whose lease is still valid, so a restarting VM cannot disturb another VM's in-flight call.
  • Audit backpressure (too many unshipped events) blocks RESERVED → SENDING; such rows wait with a renewed lease or are released when the lease lapses.

Request signing

  • Prefer an asymmetric API key (Ed25519, or RSA) if Binance accepts it for the withdrawal endpoints on your account: you generate the key pair, Binance stores only the public key, and the private key never leaves prj-exec. Otherwise use an HMAC key.
  • Signature over the exact query string sent; header X-MBX-APIKEY.
  • Clock: the VM syncs to Google's NTP; reject sending if local clock skew against Binance's GET /api/v3/time exceeds 1 s.

Reconciliation algorithm

Runs at startup and every 60 s for rows in UNKNOWN or ACCEPTED.

for each attempt in (UNKNOWN, ACCEPTED) or (FAILED by manual decision, started < 7 days ago):
    records = GET withdraw/history?withdrawOrderId=<attempt id>        # last 7 days
    if records has exactly 1 match:
        compare coin, network, address, addressTag as strings and amount AS DECIMALS
            (Binance pads amounts, e.g. "1250.50000000"; never compare amount strings)
            mismatch -> MANUAL_REVIEW + critical alert
        store binance id, txId, status
        if attempt was FAILED by manual decision -> CONFIRMED + security.late_found (critical)
        status 6        -> CONFIRMED
        status 1, 3, 5  -> FAILED
        status 0, 2, 4  -> ACCEPTED (keep polling)
    elif records has more than 1 match:
        MANUAL_REVIEW + critical alert          # should be impossible
    elif state == UNKNOWN and now - attempt_started_at > 15 min:
        MANUAL_REVIEW + page ops                # never auto-resend
    else:
        keep state, check again next cycle
  • An attempt older than 6 days still in UNKNOWN or ACCEPTED is escalated before it falls outside the 7-day query window.
  • Reconciliation never creates a request; it only reads history.
  • Confirm in the first integration test whether the history amount is the gross amount requested or net of the fee, and compare against the right value.

Storage

Verification job

  1. The event is inserted into audit_outbox in the same transaction as the state change. It carries no chain fields yet.
  2. A single shipper (one exec-worker instance holding pg_advisory_lock on a fixed key, with automatic failover when the lock holder dies) reads unshipped rows in id order, assigns the next gap-free shipped_seq, computes prev_hash (the previous event's hash) and event_hash = SHA-256(prev_hash || canonical(event with seq and prev_hash)), and writes the object gs://<audit-bucket>/prod/YYYY/MM/DD/<shipped_seq>.json with ifGenerationMatch=0 (create only). Only after the write succeeds does it record shipped_seq and shipped_at. Because one writer builds the chain, it cannot fork, and audit_outbox.id gaps from rolled-back transactions do not matter.
  3. The bucket in prj-audit has a locked retention policy; sa-exec-worker holds only roles/storage.objectCreator, so it cannot delete or replace objects.
  4. The executor refuses to move a payment from RESERVED to SENDING while more than 100 events, or events older than 60 seconds, are unshipped (audit backpressure).
  5. A redacted copy goes to stdout for Loki and Wazuh (addresses masked).

Verification job

A daily job, run with a read-only identity in prj-audit, reads objects in shipped_seq order from the last checkpoint, checks that each prev_hash equals the previous object's event_hash, recomputes every event_hash, checks that shipped_seq has no gaps, and writes a signed checkpoint. It also compares the count of shipped events with audit_outbox rows older than 5 minutes. Any break raises a critical alert to you.

Approver and Passkey administration

Only the exec-admin process in prj-exec, used by two named admins under a two-person rule, can change who may approve; nothing in TMS, the main backend, the internet-facing exec-web process or Google Workspace group membership alone grants approval rights.

Admin access: the exec-admin process on its own hostname exec-admin.<domain>, own LB backend and IAP policy, limited to two named admins: you and a security officer (a second person you designate; also the break-glass holder). Both Google accounts use FIDO2 security keys, ideally with Advanced Protection. The admin process has no Binance secret access and can change data only through the two-person functions in the database.

Two-person rule: every roster or credential change and every manual FAILED decision is proposed by one admin and confirmed by the other. The database rejects a confirmation by the proposer. Revocations and role downgrades take effect immediately at proposal (they only reduce risk) and are confirmed afterwards for the record.

Rules

  • The approver roster never syncs from any directory; IAP group membership only controls who can load the page.
  • Operators cannot change their own role or enrol for someone else; enrolment binds the code to the IAP identity that redeems it, which must match the operator's email.
  • Admins are not approvers. If you want an admin to also approve, give them a separate operator identity and accept that this concentrates power; the two-person rule still applies to their roster changes.
  • Monthly roster review by both admins, recorded as admin.roster_reviewed.

Pipeline

  1. CI (GitHub Actions): lint, unit tests, integration tests against Postgres + Binance mock, acceptance suite, dependency and container scan, SBOM. The CI identity (Workload Identity Federation, restricted to <org>/binance-exec on refs/heads/main) can only push images to the exec Artifact Registry. It cannot sign for production and has no access to prj-exec secrets.
  2. Release: Cloud Deploy release created with the image digests; the staging target rolls out automatically and runs the acceptance suite.
  3. Approve: the prod target has requireApproval: true; only you hold roles/clouddeploy.approver on it.
  4. Sign after approval: the first step of the approved prod rollout runs as the pipeline's prod execution service account, which alone has roles/cloudkms.signer on the exec-prod-release KMS key. It signs the exact digests you approved (Cosign, gcpkms://).
  5. Roll out: custom target creates new instance templates and runs MIG rolling updates, one VM at a time; workers drain (stop reserving, finish in-flight SENDING, release leases) before exit.
  6. Boot check: each VM's startup script runs cosign verify --key gcpkms://…/exec-prod-release on the image digest; if the signature is missing, the service does not start and security.image_unverified is raised. An image built from main but never approved by you therefore cannot run in production.

Runbooks

Four situations need a written procedure; in all of them the rule is the same — never resend a payment whose outcome is uncertain.

RB-1 Payment stuck in UNKNOWN or MANUAL_REVIEW

  1. Open the attempt in the admin UI; note withdraw_order_id, attempt time, last error.
  2. Check Binance withdrawal history in the Binance web console for that client ID and for amount + address in a ±30-minute window.
  3. Found → record the Binance withdrawal ID as evidence and mark CONFIRMED (or let reconciliation pick it up). Binance shows cancelled/rejected/failure → propose FAILED with that evidence; the other admin confirms.
  4. Not found after 2 hours and Binance support confirms no record → propose FAILED with the support ticket; the other admin confirms. Only then may TMS submit a new version, which needs fresh approvals and gets a new attempt number and withdrawOrderId. Reconciliation keeps watching the failed attempt for 7 days.
  5. Never ask engineering to "just re-run" the request.

RB-2 Rotate the Binance API key (every 90 days, or immediately on suspicion)

  1. In Binance, create the new key with the same restrictions (withdrawals only, IP-restricted to the exec egress IP).
  2. Add it as a new version of binance-api-key / binance-api-secret in prj-exec.
  3. Drain and roll mig-exec (Cloud Deploy redeploy of the current release); confirm service.started events and a successful history call.
  4. Delete the old key in Binance; disable the old secret versions.
  5. Record the rotation (admin.key_rotated) with the new key's restrictions output.

RB-3 Revoke an approver (leaver, lost device, suspicion)

  1. Either admin: admin UI → operator → Revoke (operator and all credentials). Effective immediately; the other admin confirms afterwards.
  2. The service voids their approvals on unreserved instructions; instructions that drop below quorum return to PENDING_APPROVAL and the affected payments are listed for ops.
  3. Check the audit trail for approvals they gave in the last 30 days.
  4. Remove them from the IAP ops group.
  5. If compromise is suspected, also run RB-4 steps 1–3.

RB-4 Suspected compromise: stop all fund movement

  1. Kill switch: resize mig-exec-worker to 0 (gcloud compute instance-groups managed resize mig-exec-worker --size=0 --region=$REGION --project=$EXEC_PROJECT). No new Binance requests can be sent; approvals can still be collected but nothing executes.
  2. In Binance, disable the API key (or delete it).
  3. Disable binance-api-key secret versions.
  4. Preserve evidence: snapshot exec VM disks, export the audit bucket listing and Cloud Audit Logs for both projects, Wazuh alerts.
  5. Investigate with the audit chain verification job and Wazuh; rotate everything the investigation touches (Binance key, mTLS keys, admin account security key if relevant).
  6. Restart only after a new key is created and a fresh deploy is approved; reconcile every UNKNOWN, ACCEPTED and SENDING row first.
