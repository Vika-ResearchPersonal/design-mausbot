Overview

v2 keeps the v1 platform unchanged and adds a Binance execution service in its own GCP project, so that compromising the main application, its load balancer or its GCP project is not enough to move funds. The service is the only holder of the Binance funding credentials. It executes a payment only after it has itself verified ops Passkey approvals bound to the exact, immutable payment instruction.

What v2 adds over v1

  • A separate execution project with its own VPC, service accounts, IAM, load balancer and deploy pipeline.
  • A trusted approval screen on its own origin (approve.<domain>), served from inside that project.
  • WebAuthn verification, an approver registry, a policy engine, a durable execution state machine and a reconciliation worker.
  • Locked egress: one static IP, allowed to reach only the Binance API hostnames.
  • A tamper-resistant audit store outside the execution servers.
  • A narrow private API from TMS / the main backend: create an instruction, read its status. Nothing else.

Scope: one region; the main platform as in v1; Binance funding operations (withdrawals and, if approved, internal transfers) moved out of the main backend.

Assumptions (change these if they don't hold):

  • Region asia-southeast1 (Singapore) or asia-southeast2 (Jakarta), chosen for data residency.
  • TMS creates payment requests and remains the system of record for business state; the execution service is the system of record for approval and execution state.
  • Ops approvers use platform Passkeys (device-bound or synced) on managed devices.
  • A public DNS name for the API (api.<domain>) and a separate one for approvals (approve.<domain>).

VM image. One Ubuntu LTS golden image with Docker, the OTel Collector and the Wazuh agent. Execution VMs use a separate hardened variant: no compilers or debug tools, Wazuh active response off.

Why APISIX standalone. APISIX reads routes from conf/apisix.yaml and has no Admin API, so there is no etcd and no admin port to protect. Changes ship through CI.

Scaling the app tier. The stateful MIG cannot autoscale; adding capacity means a VM with the next fixed IP plus the new node in apisix.yaml in one CI change.

Binance execution service

The execution service turns an immutable payment instruction plus verified Passkey approvals into exactly one Binance request, and nothing else can reach the Binance credentials.

Trust boundary

Project Holds Who has IAM roles
prj-platform Everything from v1: LB, APISIX, app, TMS, observability, Wazuh Platform team, sa-deployer

Payment instruction

Every execution-relevant field is part of the instruction, and the instruction never changes after creation. A change in TMS creates a new version, which voids all approvals of the old one.

Field Example Rule
tms_payment_uuid 3f6c…e1 From TMS; unique across all executions
version 1 Integer, +1 on any change
operation WITHDRAW From the policy's allowed list
source_account binance-main Logical name mapped to one Binance account in policy
asset USDT Upper case
amount "1250.5" Canonical decimal string: no exponent, no leading + or zeros, no trailing fractional zeros, scale ≤ asset precision
beneficiary_address T… Exactly as validated for the network; compared byte for byte
network TRX Binance network code
memo "" Empty string when not applicable, never absent
environment prod Approval invalid in any other environment
service_id binance-exec Approval invalid for any other service

Each approval adds its own fields: approval_nonce (32 random bytes, base64url), approval_expires_at (now + 5 minutes, RFC 3339 UTC), operator_id, instruction_hash.

Serialization: JSON Canonicalization Scheme (RFC 8785), UTF-8, all fields present, strings only for amounts. instruction_hash = SHA-256(canonical(instruction)). The WebAuthn challenge is SHA-256(canonical(approval_request)), where the approval request contains instruction_hash plus the approval fields above.

Approval and execution flow

  1. Create. TMS calls POST /v1/instructions over Private Service Connect with mTLS. The service validates fields and policy, stores the instruction and its hash, state PENDING_APPROVAL, and returns the id and hash.
  2. Review. The ops approver opens https://approve.<domain>/i/<id>. IAP checks their Google identity and ops group; the page is rendered by the execution service from its own stored instruction, never from TMS data.
  3. Challenge. On "Approve", the service creates the approval request, stores the challenge (unused, expires in 5 minutes), and returns it.
  4. Sign. The browser calls navigator.credentials.get with that challenge, rpId = approve.<domain>, userVerification: "required", and only that operator's credential IDs.
  5. Verify. The service checks, in one database transaction: - the challenge exists, is unexpired and unused, and is marked used now; - clientDataJSON.type = webauthn.get, challenge matches, origin is exactly https://approve.<domain>; - rpIdHash, user-present and user-verified flags, signature against the stored public key, sign counter increasing when non-zero; - the credential belongs to an active operator whose role allows this operation and amount; - the instruction is still PENDING_APPROVAL at the same version and hash.
  6. Quorum. The approval is stored. When policy is met (one approver, or two distinct approvers above the threshold), state becomes APPROVED.
  7. Reserve and send. The executor sets RESERVED only if the row is APPROVED and no other execution exists for that payment UUID, re-checks daily limits, writes SENDING durably, then calls Binance with withdrawOrderId = tms_payment_uuid (check Binance's length limit).
  8. Result. CONFIRMED, FAILED (Binance rejected before acceptance) or UNKNOWN (timeout, 5xx, connection reset). TMS reads GET /v1/instructions/<id>.

The main backend has no way to say "approved": the API has no such field, and execution starts only from approvals the service verified itself.

Policy

Policy is a YAML file in the execution repo, changed only through your approved pipeline, loaded read-only at start, and its version recorded on every decision.

Rule Starting point
Allowed operations WITHDRAW only; add internal transfers explicitly if needed
Source accounts Named list, each mapped to one Binance sub-account
Destinations Allowlist of address + network + memo; mirrored in Binance's withdrawal whitelist
Per-transaction limit Per asset, e.g. USDT 50,000
Daily limit Per asset and source account, counted over RESERVED, SENDING, UNKNOWN, CONFIRMED
Dual approval Above a per-asset threshold, two distinct operators on the same instruction version
Approval TTL 5 minutes per challenge; instruction expires after 24 hours unapproved

Execution states

PENDING_APPROVAL → APPROVED → RESERVED → SENDING → CONFIRMED | FAILED | UNKNOWN, plus EXPIRED, SUPERSEDED (new version) and MANUAL_REVIEW.

  • executions.tms_payment_uuid has a unique constraint; reservation is UPDATE … SET state='RESERVED' WHERE id=$1 AND state='APPROVED' checked for one affected row.
  • approvals is unique on (instruction_id, version, operator_id); challenges are consumed with UPDATE … SET used_at=now() WHERE id=$1 AND used_at IS NULL AND expires_at > now().

Reconciliation and restart

  • On start and every minute, the worker picks up rows in SENDING or UNKNOWN and queries Binance withdrawal history by withdrawOrderId.
  • Found → record the Binance id and status, move to CONFIRMED or FAILED. Not found after a 15-minute window → MANUAL_REVIEW. A resend then needs a new instruction version and fresh approvals; the service never resends automatically.
  • A crash between "write SENDING" and "record response" therefore always ends in reconciliation, never a blind resend.

Narrow API

Surface Endpoints Caller
Internal (PSC + mTLS) POST /v1/instructions, GET /v1/instructions/{id} TMS / main backend only
Approval origin GET /i/{id}, POST /i/{id}/challenge, POST /i/{id}/assert Ops browsers through IAP
Admin Enrol, revoke, change role You, through IAP on a separate port; never public

No pass-through endpoints, no caller-supplied URLs, no generic Binance proxy.

Passkey administration

  • Enrolment, replacement, recovery and role changes run only in the admin interface, reached through IAP with your identity and a hardware security key.
  • You issue a one-time enrolment code; the operator registers the Passkey on approve.<domain> with user verification required. New approvers and role changes take effect after 24 hours and notify all existing approvers.
  • Recovery = revoke the old credential, then enrol again through the same flow. Every step is audited.

Deployment control

  • Build in CI (GitHub Actions) with no access to prj-exec secrets; sign the image with Cosign; push to the exec Artifact Registry.
  • Deploy through a Cloud Deploy pipeline in prj-exec whose production stage requires approval; only you hold roles/clouddeploy.approver.
  • The VM startup script verifies the image signature against a pinned public key before running it. Policy files ship the same way.

Audit trail

  • Records: instruction and hash, policy version and decision, each challenge, each approval (operator, time, verification result), each execution attempt, Binance request id and response, reconciliation results. No secrets, no API signatures.
  • Each record is written as its own object to gs://<audit-bucket> in prj-audit before the next state change. The bucket has a locked retention policy; sa-exec has only storage.objectCreator. Each record carries the hash of the previous one, so gaps and edits are detectable.
  • A redacted copy goes to Loki and Wazuh for search and alerting.

Acceptance tests

Must reject or survive Test Expected
Modified details after approval Change amount in TMS after approval New version; old approvals void; nothing sent
Expired approval Sign after 5 minutes Rejected, audited
Replayed approval Resend a valid assertion Rejected: challenge already used
Unauthorized approval Revoked operator, or role below amount Rejected
Duplicate or concurrent execution Two executors and repeated calls on one payment UUID Exactly one Binance request
Threshold bypass Above-threshold payment approved once, or twice by one operator Stays PENDING_APPROVAL

Approval flag only Backend sends approved=true Rejected: unknown field, no execution
Timeout Binance mock delays past client timeout, then accepts UNKNOWN → reconciled to CONFIRMED; no second request
Restart Kill the service after SENDING On restart reconciled; no resend

Execution service telemetry rules: never log or trace request bodies to Binance, signatures, API keys, WebAuthn assertions or full addresses (log the instruction hash and a masked address). Spans carry the instruction id, state and policy decision only.

Observability VM (vm-obs)

  • e2-standard-4 to start; Docker Compose runs otel-collector-contrib, prometheus (with --web.enable-remote-write-receiver), loki (GCS backend), tempo (GCS backend, metrics-generator) and grafana.
  • Grafana data sources: Prometheus, Loki, Tempo (trace-to-logs and trace-to-metrics on), Google Cloud Monitoring and Logging.
  • Grafana admin password and OIDC client secret come from Secret Manager at boot.
  • Reached only through IAP: gcloud compute start-iap-tunnel vm-obs 3000 --local-host-port=localhost:3000.
  • The OTel gateway is also published through an internal passthrough NLB and a PSC service attachment that accepts only prj-exec.

Wazuh VM (vm-wazuh)

  • Official wazuh-docker single-node deployment. Start at 4 vCPU / 16 GB RAM and a 200 GB SSD disk. Set vm.max_map_count=262144 for the indexer.
  • Agents are baked into the golden image and enrol with wazuh-enrollment-password from Secret Manager; manager 10.10.3.20, ports 1515 and 1514. Execution VMs reach the manager through their own PSC endpoint and use a separate enrolment password stored in prj-exec.
  • Turn on FIM for /etc, /opt/apisix, /opt/exec, Docker configs; SCA with the CIS Ubuntu benchmark; vulnerability detection; Docker listener; log analysis.
  • On execution VMs: active response off and remote commands off (w``azuh_command.remote_commands=0 and sca.remote_commands=0 in local_internal_options.conf), so a compromised Wazuh manager cannot run commands there.
  • GCP feed: Cloud Logging sinks from both projects to Pub/Sub; the gcp-pubsub module pulls with the one keyed service account (subscriber-only, key in Secret Manager, rotated every 90 days).
  • Execution-specific rules: approver added or role changed, policy version changed, execution reaching UNKNOWN or MANUAL_REVIEW, rejected approvals above 3 in 10 minutes, any Secret Manager access to the Binance secret by an identity other than sa-exec.
  • Dashboard reached only through IAP on port 443.

Security design

Security is layered: Cloud Armor filters at Google's edge, APISIX authenticates and throttles per consumer, IAM limits each VM to the secrets and images it needs, and fund movement sits behind a separate project boundary that only you administer.

IAP on the approval backend adds a Google identity check for the ops group before the page loads; the Passkey assertion is then the approval itself.

TLS

  • Client to LBs: Google-managed certificates, SSL policy MODERN, minimum TLS 1.2, HSTS on approve.<domain>.
  • TMS to execution API: mTLS over PSC. The service accepts only the TMS client certificate (issued from a private CA in prj-exec).
  • LB to APISIX and APISIX to app: HTTP inside the VPC is acceptable for many workloads; switch to HTTPS if your regulator requires encryption in transit inside the VPC.
  • Execution service to Cloud SQL: TLS with sslmode=verify-full or the Cloud SQL Auth Proxy.
  • Telemetry and Wazuh: TLS on the OTLP receiver; Wazuh agent traffic is encrypted by default.

Secret handling

  1. Store each credential as its own secret, regional replication in the deployment region.
  2. At boot, a startup script reads the secrets with the VM's identity and writes them to a tmpfs file readable only by the container user.
  3. Docker gets them as an env file or a mounted file; APISIX references them as $ENV://NAME, so no secret value is stored in Git.
  4. Rotation = add a new secret version, then roll the MIG.
  5. Binance key: created by you in Binance with only the permissions needed (enable withdrawals; no trading, no futures, no universal transfer unless required), restricted to the exec static egress IP, with Binance's withdrawal address whitelist on. Rotate it at cutover and every 90 days; old keys from the main app are deleted in Binance.

VM hardening

  • Shielded VM (Secure Boot, vTPM, integrity monitoring); OS Login on; serial port off; project-wide SSH keys blocked.
  • Containers run as a non-root user, read-only root filesystem, no-new-privileges, only needed ports published.
  • Images pinned by digest; Artifact Registry vulnerability scanning on.
  • Execution VMs: separate minimal image, signature check at boot, no SSH except break-glass, no package managers reachable (egress denied).

19. Build and deploy pipeline

  • New repository (or protected directory) binance-exec, with branch protection and you as required reviewer for policy/ and deploy/.
  • GitHub Actions authenticates to prj-exec through Workload Identity Federation as a build identity that can only push to the exec Artifact Registry. It signs the image with Cosign.
  • Cloud Deploy pipeline in prj-exec with a custom target that rolls mig-exec to a new instance template; the prod target has requireApproval: true, and only you hold roles/clouddeploy.approver.
  • The exec startup script verifies the image signature with cosign verify --key <pinned-public-key> before docker run; on failure the VM does not start the service and alerts.

20. Build the service

Modules: canonicalizer (RFC 8785), instruction store, WebAuthn verifier (py_webauthn, SimpleWebAuthn server or webauthn4j), policy engine, approval UI, executor, Binance client (fixed endpoints), reconciliation worker, audit writer, admin UI. Core schema:

CREATE TABLE instructions (
  id uuid PRIMARY KEY,
  tms_payment_uuid uuid NOT NULL,
  version int NOT NULL,
  canonical_json bytea NOT NULL,
  instruction_hash bytea NOT NULL,
  state text NOT NULL,
  policy_version text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tms_payment_uuid, version)
);
CREATE TABLE challenges (
  id uuid PRIMARY KEY,
  instruction_id uuid NOT NULL REFERENCES instructions,
  operator_id uuid NOT NULL,
  approval_request bytea NOT NULL,
  challenge bytea NOT NULL UNIQUE,
  expires_at timestamptz NOT NULL,
  used_at timestamptz
);
CREATE TABLE approvals (
  instruction_id uuid NOT NULL REFERENCES instructions,
  operator_id uuid NOT NULL,
  credential_id bytea NOT NULL,
  challenge_id uuid NOT NULL UNIQUE REFERENCES challenges,
  verified_at timestamptz NOT NULL,
  PRIMARY KEY (instruction_id, operator_id)
);
CREATE TABLE executions (
  tms_payment_uuid uuid PRIMARY KEY,          -- one execution per payment, ever
  instruction_id uuid NOT NULL REFERENCES instructions,
  state text NOT NULL,
  withdraw_order_id text NOT NULL UNIQUE,
  binance_id text,
  updated_at timestamptz NOT NULL DEFAULT now()
);

The application database user has no DELETE on these tables and no UPDATE on instructions.canonical_json or instruction_hash (column-level grants).

21. Binance key and cutover

  1. In Binance, create a new API key for the funding sub-account: withdrawals only, IP restricted to ip-exec-egress, withdrawal address whitelist on with the policy's destinations.
  2. Store it in prj-exec Secret Manager; deploy the service; run the acceptance tests against Binance's test environment or a mock, then one small real withdrawal with dual approval.
  3. Switch TMS to POST /v1/instructions on 10.10.2.50:8443.
  4. Remove the old Binance code paths and configuration from the main backend; delete the old Binance secrets from prj-platform.
  5. Delete every old Binance API key in Binance. Confirm in Binance's API management page that only the new key exists.
