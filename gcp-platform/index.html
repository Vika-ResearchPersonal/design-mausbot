Overview

Internet traffic enters through one global external Application Load Balancer with Cloud Armor, reaches Apache APISIX on a private VM group, and APISIX proxies directly to the application containers on a second private VM group. No VM has a public IP. Every VM ships traces, metrics and logs through OpenTelemetry to a self-hosted Grafana stack (Prometheus, Loki, Tempo), and runs a Wazuh agent that reports to a Wazuh SIEM. Secrets live only in Secret Manager and are read with each VM's own service account.

Scope: one GCP project, one region, HTTPS APIs served from Docker containers on Compute Engine VMs.

Assumptions (change these if they don't hold):

  • Region asia-southeast2 (Jakarta) or asia-southeast1 (Singapore), chosen for data residency.
  • Container images are built by CI and pushed to Artifact Registry.
  • A public DNS name you control, for example api.example.com.

Architecture

Request path. Client → HTTPS 443 on the global LB → Cloud Armor evaluates the request at Google's edge → LB forwards to an APISIX VM on port 9080 → APISIX checks auth and rate limits, then load-balances across the app VMs on 10.10.2.11–.13:8080.

Telemetry path. APISIX and the app send traces over OTLP to the OpenTelemetry Collector on their own VM, which also scrapes Prometheus metrics and tails Docker logs. It forwards everything to the gateway collector on the observability VM, which writes metrics to Prometheus, logs to Loki and traces to Tempo. Grafana reads all three.

Security path. The Wazuh agent on every VM sends events to the Wazuh manager on 1514/tcp. Cloud Logging (audit, LB and Cloud Armor logs) reaches Wazuh through a log sink and Pub/Sub.

Boot. Each VM reads its secrets from Secret Manager and pulls its image from Artifact Registry over Private Google Access. Cloud NAT and IAP are not drawn.

VM image. Use one Ubuntu LTS golden image for every VM, with Docker Engine, the OTel Collector and the Wazuh agent preinstalled. Container-Optimized OS is smaller and read-only, but it cannot install host packages, so it would need the collector and Wazuh agent as containers, which weakens host-level monitoring. Build an instance template per release and roll it out through the MIG.

Why APISIX standalone. In standalone mode APISIX reads routes, upstreams and consumers from conf/apisix.yaml and has no Admin API, so there is no etcd cluster to run and no admin port to protect. A config change is a new file shipped by CI followed by a MIG rolling restart (or a file reload, which APISIX picks up automatically).

Scaling the app tier. A stateful MIG cannot autoscale, so adding capacity means adding a VM with the next fixed IP and adding that IP to apisix.yaml in the same CI change. If you need autoscaling later, either run the app containers on the APISIX VMs (upstream 127.0.0.1:8080, both tiers scale together) or bring back an internal LB.

Observability and security monitoring

One OpenTelemetry pipeline carries all three signals to self-hosted backends, and Wazuh watches every host; both stacks live in a separate snet-ops subnet that the workload VMs can only push to.

Signal flow

Signal Source Collected by Stored in Retention (starting point)
Traces APISIX opentelemetry plugin, app OTel SDK OTLP → local collector → gateway collector (tail sampling: keep errors + slow, 10% of the rest) Tempo, GCS bucket PROJECT-tempo 14 days
Metrics APISIX prometheus plugin (:9091), app /metrics, hostmetrics, docker_stats Local collector scrapes → gateway collector → Prometheus remote write Prometheus, SSD persistent disk 30 days
Logs Docker JSON logs (APISIX access log, app logs), syslog Local collector filelog receiver → gateway collector → Loki OTLP endpoint Loki, GCS bucket PROJECT-loki 30 days
Cloud logs LB, Cloud Armor, audit logs Stay in Cloud Logging; Grafana's Google Cloud Logging data source for ad-hoc views Cloud Logging per log bucket
Security events Wazuh agents (FIM, SCA, rootcheck, log analysis, vulnerability detection); Cloud Logging via Pub/Sub Wazuh manager Wazuh indexer 90 days hot, then snapshot to GCS

APISIX writes the trace ID into its access log (opentelemetry plugin with set_ngx_var: true, $opentelemetry_trace_id in the log format), so Grafana jumps from a Tempo trace to its Loki log lines and back.

Observability VM (vm-obs)

  • e2-standard-4 to start; Docker Compose runs otel-collector-contrib, prometheus (with --web.enable-remote-write-receiver), loki (GCS backend), tempo (GCS backend, metrics-generator writing service-graph metrics to Prometheus) and grafana.
  • Grafana data sources: Prometheus, Loki, Tempo (trace-to-logs and trace-to-metrics links on), Google Cloud Monitoring and Logging through the VM's service account.
  • Grafana admin password and OIDC client secret come from Secret Manager at boot.
  • Reached only through IAP: gcloud compute start-iap-tunnel vm-obs 3000 --local-host-port=localhost:3000.
  • Alerting from Grafana to your chat or on-call tool; the alert rules are listed under Operations.

Wazuh VM (vm-wazuh)

  • Official wazuh-docker single-node deployment (manager, indexer, dashboard). Start at 4 vCPU / 16 GB RAM and a 200 GB SSD disk, then size by agent count and retention. Set vm.max_map_count=262144 on the host for the indexer.
  • Agents are baked into the golden image and enrol on first boot with an enrolment password from Secret Manager (wazuh-enrollment-password), manager address 10.10.3.20, ports 1515 (enrol) and 1514 (events).
  • Turn on: file integrity monitoring for /etc, /opt/apisix, Docker configs; SCA with the CIS Ubuntu benchmark; vulnerability detection; Docker listener module; log analysis of auth.log and APISIX access logs.
  • GCP feed: a Cloud Logging sink (admin activity + data access audit logs, LB and Cloud Armor logs) to a Pub/Sub topic; the Wazuh gcp-pubsub module pulls from the subscription. That module authenticates with a service-account key file, so it is the one keyed account in the design: give it only roles/pubsub.subscriber on that subscription, keep the key in Secret Manager, write it to tmpfs at boot, rotate every 90 days.
  • Leave active response (automatic IP blocking) off until rules are tuned; block at Cloud Armor instead.
  • Dashboard reached only through IAP on port 443; admin and API credentials in Secret Manager.

Network design

One custom-mode VPC with three subnets; only Google's load balancer ranges reach the gateway, only APISIX reaches the app, and workload VMs can only push telemetry and security events to the ops subnet.

Subnet Example CIDR Purpose Notes
snet-gateway 10.10.1.0/24 APISIX VMs Private Google Access on
snet-app 10.10.2.0/24 App VMs at fixed IPs .11–.13 Private Google Access on
snet-ops 10.10.3.0/24 vm-obs (.10), vm-wazuh (.20) Private Google Access on; static internal IPs

Firewall rules (VPC firewall policy or VPC rules; deny everything else by default):

Name Direction Source Target (service account) Port
allow-glb-to-apisix Ingress 35.191.0.0/16, 130.211.0.0/22 (Google Front End + health checks) sa-apisix tcp:9080
allow-apisix-to-app Ingress sa-apisix sa-app tcp:8080
allow-hc-to-app Ingress 35.191.0.0/16, 130.211.0.0/22 (MIG autohealing checks) sa-app tcp:8080
allow-otlp-to-obs Ingress sa-apisix, sa-app, sa-wazuh sa-obs tcp:4317, tcp:4318
allow-agents-to-wazuh Ingress sa-apisix, sa-app, sa-obs sa-wazuh tcp:1514, tcp:1515
allow-iap-admin Ingress 35.235.240.0/20 (IAP) all VMs tcp:22; plus tcp:3000 on sa-obs, tcp:443 on sa-wazuh
deny-all-ingress Ingress 0.0.0.0/0 all all, lowest priority

Target firewall rules by service account, not network tag: only users with iam.serviceAccountUser can attach a service account, while anyone who can edit a VM can change its tags.

Egress. VMs have no external IP. Cloud NAT on a Cloud Router gives them outbound internet; Private Google Access sends Secret Manager, Artifact Registry and Logging calls over Google's network. If you need to stop data exfiltration to arbitrary hosts, add egress firewall rules or a Secure Web Proxy allowlist.

Security design

Security is layered: Cloud Armor filters at Google's edge, APISIX authenticates and throttles per consumer, and IAM limits each VM to the secrets and images it needs.

Cloud Armor policy waf-edge

Start every WAF rule in preview mode for about a week, review the logs for false positives, then switch to enforce.

Priority Rule Action
100 Allowlist: office / partner CIDRs (optional) allow
200 Denylist: known bad IPs, or geo block with origin.region_code deny(403)
1000 evaluatePreconfiguredWaf('sqli-v33-stable', {'sensitivity': 1}) deny(403)
1010 xss-v33-stable deny(403)
1020 lfi-v33-stable, rfi-v33-stable deny(403)
1030 rce-v33-stable deny(403)
1040 methodenforcement-v33-stable, protocolattack-v33-stable deny(403)
1050 scannerdetection-v33-stable, sessionfixation-v33-stable deny(403)
2000 Rate-based ban per client IP (for example 600 requests / 60 s, ban 300 s) rate_based_ban, 429
2147483647 Default allow

Also turn on Adaptive Protection (layer-7 DDoS anomaly detection) and set --json-parsing=STANDARD so WAF rules inspect JSON bodies field by field. Begin at sensitivity 1 and raise it only after tuning.

TLS

  • Client to LB: Google-managed certificate, SSL policy MODERN, minimum TLS 1.2, HTTP redirects to HTTPS.
  • LB to APISIX and APISIX to app: HTTP inside the VPC is acceptable for many workloads. If your regulator requires encryption in transit inside the VPC, set the backend service protocol to HTTPS with a private-CA certificate on APISIX, and use an APISIX upstream with scheme: https (or mTLS) to the app.
  • Telemetry and Wazuh: enable TLS on the gateway collector's OTLP receiver; Wazuh agent traffic is encrypted by default.

Identity and IAM

Service account Roles (granted on the narrowest resource)
sa-apisix secretmanager.secretAccessor on gateway secrets + wazuh-enrollment-password; artifactregistry.reader on the repo; storage.objectViewer on the config bucket
sa-app secretmanager.secretAccessor on app secrets + wazuh-enrollment-password; artifactregistry.reader
sa-obs storage.objectAdmin on the Loki and Tempo buckets; secretmanager.secretAccessor on Grafana secrets; monitoring.viewer and logging.viewer for Grafana's Google Cloud data sources
sa-wazuh secretmanager.secretAccessor on Wazuh secrets; storage.objectAdmin on the Wazuh snapshot bucket
sa-wazuh-pubsub (keyed, see Wazuh) pubsub.subscriber on the Wazuh subscription only
sa-deployer (CI, through Workload Identity Federation) compute.instanceAdmin.v1, iam.serviceAccountUser on the VM accounts, artifactregistry.writer, storage.objectAdmin on the config bucket

No service-account key files except the one Wazuh Pub/Sub reader. Humans reach VMs through IAP + OS Login (roles/iap.tunnelResourceAccessor, roles/compute.osLogin).

Secret handling

  1. Store each credential as its own secret (db-password, jwt-signing-key, apisix-consumer-partner-a), regional replication in the deployment region.
  2. At boot, a startup script reads the secrets with the VM's metadata-server identity (gcloud secrets versions access latest --secret=…) and writes them to a tmpfs file readable only by the container user.
  3. Docker gets them as an env file or a mounted file; APISIX references them as $ENV://NAME in apisix.yaml, so no secret value is stored in Git.
  4. Rotation = add a new secret version, then roll the MIG. Pin versions (versions/7) instead of latest if you need controlled rollouts.

APISIX also has a native GCP Secret Manager provider ($secret://gcp/…), but it authenticates with a service-account key JSON. Avoid it here; the boot-time fetch keeps you keyless.

VM hardening

  • Shielded VM (Secure Boot, vTPM, integrity monitoring); OS Login on; serial port off; project-wide SSH keys blocked.
  • Containers run as a non-root user, read-only root filesystem, no-new-privileges, only the needed ports published.
  • Images pinned by digest; Artifact Registry vulnerability scanning on; optionally Binary Authorization-style signing in CI.

Implementation steps

Build bottom-up: network and identity first, then secrets, then VMs, and the public LB with Cloud Armor last, so nothing is exposed before it is protected. Run steps 9 and 10 (observability and Wazuh VMs) before you start the gateway and app groups in steps 7 and 8, so every workload VM is watched from first boot. Commands use these variables:

export PROJECT_ID=my-project REGION=asia-southeast2 ZONE=asia-southeast2-a DOMAIN=api.example.com
for N in apisix app obs wazuh; do
  export SA_${N^^}=sa-${N}@${PROJECT_ID}.iam.gserviceaccount.com
done
gcloud config set project $PROJECT_ID

7. Gateway VM startup script and MIG

startup-apisix.sh (Ubuntu LTS image with Docker Engine; on Container-Optimized OS use the Secret Manager REST API with a metadata-server token instead of gcloud):

#!/bin/bash
set -euo pipefail
mkdir -p /opt/apisix /run/secrets && mount -t tmpfs -o size=1m,mode=0700 tmpfs /run/secrets

# Wazuh agent (installed in the golden image, not yet started)
gcloud secrets versions access latest --secret=wazuh-enrollment-password > /var/ossec/etc/authd.pass
chown root:wazuh /var/ossec/etc/authd.pass && chmod 640 /var/ossec/etc/authd.pass
sed -i 's|<address>.*</address>|<address>10.10.3.20</address>|' /var/ossec/etc/ossec.conf
systemctl enable --now wazuh-agent

# OTel Collector agent (config baked into /etc/otelcol-contrib/config.yaml)
systemctl enable --now otelcol-contrib

# APISIX
gcloud storage cp gs://PROJECT_ID-apisix-config/{config.yaml,apisix.yaml} /opt/apisix/
echo "PARTNER_A_JWT_SECRET=$(gcloud secrets versions access latest --secret=apisix-partner-a-jwt)" > /run/secrets/apisix.env
chmod 600 /run/secrets/apisix.env
docker rm -f apisix 2>/dev/null || true
docker run -d --name apisix --restart=always --network=host \
  --env-file /run/secrets/apisix.env --read-only --tmpfs /usr/local/apisix/logs --tmpfs /tmp \
  --security-opt no-new-privileges \
  -v /opt/apisix/config.yaml:/usr/local/apisix/conf/config.yaml:ro \
  -v /opt/apisix/apisix.yaml:/usr/local/apisix/conf/apisix.yaml:ro \
  apache/apisix:<pinned-version>

APISIX runs with --network=host so it reaches the collector on 127.0.0.1:4318, and the collector scrapes APISIX metrics on 127.0.0.1:9091. Firewall rules still allow only port 9080 in from outside.

gcloud compute instance-templates create tpl-apisix-v1 --machine-type=e2-standard-2 \
  --region=$REGION --subnet=snet-gateway --no-address \
  --service-account=$SA_APISIX --scopes=cloud-platform \
  --image-family=<ubuntu-lts-family-with-docker-or-your-golden-image> --image-project=<project> \
  --shielded-secure-boot --shielded-vtpm --shielded-integrity-monitoring \
  --metadata=enable-oslogin=TRUE,block-project-ssh-keys=TRUE \
  --metadata-from-file=startup-script=startup-apisix.sh

gcloud compute health-checks create http hc-apisix --port=9080 --request-path=/healthz
gcloud compute instance-groups managed create mig-apisix --region=$REGION \
  --template=tpl-apisix-v1 --size=2 --health-check=hc-apisix --initial-delay=120
gcloud compute instance-groups managed set-named-ports mig-apisix --region=$REGION --named-ports=http:9080
gcloud compute instance-groups managed set-autoscaling mig-apisix --region=$REGION \
  --min-num-replicas=2 --max-num-replicas=6 --target-cpu-utilization=0.6

Build one golden image (Packer) for every VM: Ubuntu LTS, Docker Engine, otelcol-contrib with the agent config from step 9, and the Wazuh agent pinned to the manager's version (installed, not started). Faster scale-out, no dependency on package mirrors at boot, and every VM is watched from its first minute.

8. App tier: stateful MIG with fixed IPs

The app VMs use the same golden image; startup-app.sh starts the Wazuh agent and collector exactly as in step 7, fetches db-password, and runs the app image from Artifact Registry by digest, publishing port 8080 and pointing its OTel SDK at http://127.0.0.1:4318.

gcloud compute instance-templates create tpl-app-v1 --machine-type=e2-standard-2 \
  --region=$REGION --subnet=snet-app --no-address \
  --service-account=$SA_APP --scopes=cloud-platform \
  --image=<golden-image> --shielded-secure-boot --shielded-vtpm --shielded-integrity-monitoring \
  --metadata=enable-oslogin=TRUE,block-project-ssh-keys=TRUE \
  --metadata-from-file=startup-script=startup-app.sh

gcloud compute health-checks create http hc-app --port=8080 --request-path=/healthz
gcloud compute instance-groups managed create mig-app --region=$REGION \
  --template=tpl-app-v1 --size=0 --health-check=hc-app --initial-delay=120 \
  --instance-redistribution-type=NONE

for i in 1 2 3; do
  gcloud compute instance-groups managed create-instance mig-app --region=$REGION \
    --instance=app-$i --stateful-internal-ip=interface-name=nic0,address=10.10.2.1$i,auto-delete=never
done

Autohealing recreates a failed VM with the same name and IP, so APISIX's upstream list never changes. APISIX's active health checks take a VM out of rotation within about 15 seconds; MIG autohealing replaces it.

13. DNS and verification

  1. Point an A record for $DOMAIN at ip-api; the managed certificate turns ACTIVE once DNS resolves (often 15–60 minutes).
  2. curl -i https://$DOMAIN/healthz returns 200.
  3. A call to /api/orders/ without a JWT returns 401 from APISIX; with a valid JWT it returns the app's response.
  4. curl "https://$DOMAIN/api/orders/?id=1%27%20OR%201=1" shows a preview match in Cloud Armor logs; after tuning, remove --preview and expect 403.
  5. Check the backend VMs have no external IP and SSH works only through gcloud compute ssh --tunnel-through-iap.

Observability and security checks:

  1. In Grafana Explore, a /api/orders/ request appears in Tempo as an APISIX span with a child app span, and "Logs for this span" opens the matching Loki lines (same trace_id).
  2. Prometheus shows apisix_http_status and host metrics for every VM; stop one app VM and confirm APISIX marks it unhealthy and traffic continues.
  3. The Wazuh dashboard lists every VM as an active agent; editing a file under /opt/apisix raises a file-integrity alert; a Cloud Armor block appears in Wazuh through the Pub/Sub feed.

Operations

Every change ships as a new instance template rolled through the MIG; nobody edits a running VM.

Area Practice
Deploy app CI builds image → pushes to Artifact Registry → creates tpl-app-vN with the new digest → gcloud compute instance-groups managed rolling-action start-update mig-app --region=$REGION --version=template=tpl-app-vN --max-surge=0 --max-unavailable=1 (stateful MIGs replace in place, one VM at a time)
Deploy gateway config CI validates apisix.yaml (run APISIX in a container and hit test routes), uploads to the bucket, then rolling-action replace mig-apisix
Scale app tier Add app-4 at 10.10.2.14 and add the node to apisix.yaml in the same CI change
Rollback start-update back to the previous template; keep the last 3 templates
Scaling gateway Autoscaler on CPU 60%, 2–6 VMs
Dashboards Grafana: APISIX (requests, 4xx/5xx, p95 latency, upstream health), app RED metrics, host and Docker resources, Tempo service graph
Alerts (Grafana) 5xx > 1% for 5 min; p95 > 1 s; an APISIX upstream node unhealthy; disk > 80% on any VM; collector export failures; no data from a VM for 10 min
Alerts (Wazuh) Rule level ≥ 10 to the security channel: FIM changes on config paths, new critical CVEs, SCA failures, IAM changes and secret access by unexpected principals from audit logs
Alerts (Cloud) Cloud Armor deny spike and Adaptive Protection alerts in Cloud Monitoring, as a backstop if the Grafana VM is down
Ops stack health Grafana and Wazuh are single VMs: snapshot their disks daily; Loki and Tempo data is already in GCS; Wazuh indexer snapshots to GCS
Audit Data Access audit logs on for Secret Manager; audit logs to Wazuh and to a locked log bucket for retention
Patching Rebuild the golden image monthly (or on critical CVEs, which Wazuh flags) and roll every group; pin and upgrade the Grafana stack and Wazuh images on a schedule

Risks and open decisions

Risk Impact Mitigation
WAF false positives block real users Failed API calls after go-live Preview mode first, tune per-rule sensitivity, add rule exclusions for known fields
App tier cannot autoscale Traffic spikes need a manual change Size for peak + headroom; adding a VM is a small CI change; move app onto the APISIX VMs or add an internal LB if autoscaling becomes a must
APISIX upstream list drifts from real VMs Requests to a dead IP until health checks eject it Fixed IPs from the stateful MIG; one CI change updates both; alert on unhealthy upstream nodes
Observability and Wazuh are single VMs Loss of dashboards or SIEM during an outage; telemetry gaps Disk snapshots, GCS-backed Loki/Tempo, Wazuh snapshots; Cloud Monitoring alerts as backstop; move to a 2-node setup later
One keyed service account (Wazuh Pub/Sub) Key leak exposes the log feed Subscriber-only on one subscription, key in Secret Manager, 90-day rotation
Telemetry unencrypted inside the VPC May fail an in-transit encryption check TLS on the OTLP receiver and agent exporter before production
Single region Region outage takes the API down Accept for now; a second region adds another set of groups behind the same global LB
Secrets fetched only at boot Rotation needs a rolling restart Rolling replace in the rotation runbook

Open decisions

  • Region: Jakarta (asia-southeast2) or Singapore (asia-southeast1)
  • App tier size and whether a fixed-size group is acceptable, or app containers should share the APISIX VMs
  • Authentication at APISIX: jwt-auth with your own keys, or openid-connect against an IdP
  • Encryption inside the VPC (APISIX to app, OTLP): required or not
  • Retention for metrics, logs, traces and Wazuh alerts, set against your audit requirements
  • Where Grafana and Wazuh alerts go (Slack, email, on-call tool)
  • Infrastructure as code: turn these steps into Terraform modules before production
